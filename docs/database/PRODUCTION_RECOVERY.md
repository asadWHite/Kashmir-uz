## Schema and migration architecture

`src/db/schema.ts` defines all 14 tables. The baseline is Drizzle-generated DDL:
all columns, lengths, nullability, defaults, serial PK/owned sequences, unique
email/slugs, category SET NULL FK, session CASCADE FK, translation locale CHECK,
translation uniqueness/search indexes and descending history indexes. SQL-only
legacy constraints/indexes have been brought into Drizzle without adding fields.
Explicit DESC NULLS LAST differs textually from historical default NULLS FIRST,
but the indexed timestamps are NOT NULL. No update triggers: callers set
updated_at. Polymorphic translation/revision entity IDs intentionally have no FK.

`migrations/0000_production_baseline.sql` creates schema ONLY. It has no transaction
wrappers because `scripts/db-migrate.ts` owns transactions. Existing 0001/0002
are historical, subsumed by baseline and excluded from the explicit allowlist.
0003 is optional legacy demo translation backfill: **DO NOT APPLY** in recovery.
`src/db/seed.ts` is also forbidden in production (demo records, default password,
and overwrite behavior). No build/start hooks migrate or seed.

Runner validates the PostgreSQL URL, refuses Neon pooler endpoints (session locks
require a direct connection), checks current database/schema, acquires a
nonblocking session advisory lock, validates strict ordering and SHA-256 history,
then applies each unrecorded allowlisted migration transactionally. The ledger
`public.kashmir_migrations` stores ID/checksum/applied_at. Both DDL and successful
ledger insert commit together. Failed migration rolls back and reports its ID.
Advisory locks serialize THIS runner, not arbitrary third-party SQL: freeze other
DDL during recovery. `DATABASE_URL` is the only target; no localhost fallback in
tooling. Drizzle config is generation-only, with no embedded connection string.

**Nonempty untracked database:** runner deliberately refuses adoption, even if
objects look compatible. Do not mark history manually or add IF NOT EXISTS to
hide drift. Have an engineer review read-only verification, provenance and
additive reconciliation/adoption in a separate change. Never drop/reset objects.
A failed first migration may leave an EMPTY ledger, which is safe to retry.

## Verification design

`npm run db:verify` opens a repeatable-read READ ONLY transaction. It compares
catalog columns/types/nullability/default expressions/identity, PK/FK/unique/CHECK
(validation included), index definition/readiness/validity, and owned serial
sequence definitions (not current counters). Ledger shape, PK and exact ordered
checksums are checked separately. Missing/different expected objects FAIL;
extra objects produce WARNING and are preserved. Operational identity/login are
explicitly NOT VERIFIED. Public health exposes only statuses, never definitions.

Catalog reference JSON is generated by PostgreSQL from reviewed DDL, NOT hand-
authored. A runtime Drizzle model contract rejects stale references; an independent
automated Drizzle generation comparison proves baseline matches source. References
were regenerated and validated on native PostgreSQL 18.6. PostgreSQL major-version
pretty-printing differences may produce conservative FAIL: investigate and review,
never bypass verification. No complete PASS is inferred from `SELECT 1`.

For baseline maintenance only, on a **new empty loopback disposable** DB named
with `_test` suffix, regenerate and review references:

```sh
# TEST_DATABASE_URL provisioned securely in your shell, never the production URL
npx tsx scripts/db-reference.ts
npm run test:database
```

Reference generator checks source/baseline equality, executes DDL in a rolled-back
transaction and refuses nonlocal/nonempty targets. For subsequent releases append
reviewed DDL to the manifest, retaining old IDs/checksums; update reference-generation
and source-diff tests to replay the full approved history before updating references.
Never edit an already deployed baseline. New references describe final intended
schema; runner validates that final state inside the last pending migration
transaction and on no-op reruns. No automatic down/reset.

## Failure / rollback / troubleshooting

- Missing DATABASE_URL, invalid URL, pooler endpoint: configure confirmed direct
  PostgreSQL target securely. No implicit host or secret is printed.
- Connection timeout/TLS/permission failure: inspect Neon status, role privileges,
  network and TLS configuration privately. New commands redact raw error text;
  only safe error code is emitted. Production hostname unreachable from this
  sandbox is NOT evidence the deployed service is broken.
- Concurrent runner: stop/retry after owner completes; do not forcibly unlock an
  unknown live operator. Connection loss releases session lock automatically.
- SQL failure: current transaction rolled back, failed ID unrecorded. Fix the
  cause/permissions and rerun; successful prior migrations stay recorded. Never
  mutate deployed checksums/history to silence drift. A process loss after COMMIT
  is safe: next run checks ledger.
- Verification FAIL: do not initialize admin/deploy. Review catalog differences,
  Drizzle and approved history; add reviewed non-destructive repair if necessary.
  Extra objects are warnings, not permission to remove them.
- Login 401: missing admin/wrong password/normalization. Login 503: DB query or
  signing failure; verify schema/history, then AUTH_SECRET. Never expose hashes.
- Unchanged old health behavior: confirm deployed SHA/production domain, not Preview.
- App rollback: redeploy last compatible application artifact without reversing
  additive DB objects. Baseline has no destructive down migration. Data corruption
  recovery requires approved Neon PITR/backup procedure into a separate recovery
  branch followed by review; never delete the active project.

## Security review / limitations

No auth replacement. Existing scrypt salt/hash format is preserved; hashes and
passwords never logged by new tooling. Existing cookies and JWT expiration are
preserved. Middleware now uses the same role/payload verification as the server
(previously signature-only middleware accepted wrong-role signed JWTs).

Existing JWT logout clears cookie and records logout but does not revoke a copied
JWT before its 7-day expiration; session history remains optional. Account status
and password rotation fields do not exist. Configure durable Vercel WAF login
rate limits and monitor abuse; in-memory per-instance limiting is not a durable
solution. Existing server-side error logging in older handlers should be reviewed
for redaction separately; new diagnostics/tooling never emit raw SQL errors.
No unrelated design/frontend changes or new package dependencies were introduced.
