Its constraint-name lookup is not restricted to the target table; IF NOT EXISTS also does not validate an existing column or index. Review before use, especially if partially applied.

Serverless instances multiply pool usage; check Neon compute wake time, pooler mode, metrics, timeouts and connection counts before tuning. There is no production performance evidence here. Avoid logging connection strings or query parameters.

## Separate targets and read-only inspection

1. In Vercel inspect **Production** `DATABASE_URL` privately and identify the actual deployed environment and latest deployment; compare its endpoint to Neon console project, branch, database and pooler/direct endpoints. Do not print/copy credentials into chat, shell history, logs or repository. Record non-secret project ID, branch ID, database name and deployment ID. Preview and local URLs must be separately identified and must not default to production. Do not change the production target.
2. In Neon verify the endpoint maps to the same branch and database. Confirm that the audited connection is the one used by the deployment, including Vercel environment scope, deployment overrides and any endpoint options. `current_database()` alone cannot prove a Neon branch or endpoint identity. Use read-only credentials for inspection where possible and verify permissions are sufficient to see all catalog objects.
3. In a private environment set `DATABASE_URL` securely without echoing it, then run `npx tsx scripts/db-gate.ts --verify`. It starts a read-only transaction, checks every Drizzle table and column for type, nullability and default **presence**, and lists catalog defaults, constraints and indexes. Inspect all definitions manually against `src/db/schema.ts` and SQL files, including PK/unique/FK targets, delete actions, index keys, uniqueness, validity, predicates, check validity, and exact default/sequence definitions. The script does not automatically compare these definitions and a zero exit status is not complete verification. Output can contain database identifiers or literal default expressions; review and redact before sharing. An absent table or missing catalog permissions must be investigated, never inferred from empty output alone.
4. Inspect Drizzle tracking table(s) listed by the tool, if present, in a read-only session. Compare their hashes/timestamps with independently retained deployment records; manual SQL migrations are not automatically recorded there. Check Neon history and deployment logs for partial runs or direct changes. Compare independently audited local/preview/production targets. No reliable conclusion is possible if logs are unavailable.
5. Gather safe pre-change evidence: row counts, non-secret product identifiers and hashes of key content/gallery fields using a private read-only session, plus Neon point-in-time restore or a tested backup. Do not export sensitive customer/admin data into logs or the repository. Check concurrent writes and establish an appropriate maintenance window so comparisons are meaningful.

## Review and execute only after target verification

* Write an exact discrepancy-specific plan from the catalog evidence, including all tables/columns/types/defaults/nullability, constraints and indexes. Consult a PostgreSQL operator for populated tables and dependencies. Review locks, existing rows, duplicates, orphaned foreign keys, privilege and rollback/recovery strategy. Rehearse on a disposable Neon branch restored from production; confirm target before each operation. No drops, resets, destructive casts, table recreation or record deletion. Stop if proposed DDL may rewrite, truncate, overwrite or block critical traffic.
* If and only if entirely missing and prerequisites match, `0001` or `0002` can be considered as a starting point. Review their full SQL and idempotency limitations first. An existing partial or incompatible table requires separately reviewed additive SQL tailored to its actual contents, not blindly rerunning the file. Index creation may lock writes; plan accordingly. `0003` is optional content backfill requiring business approval and per-row review; do not treat it as required DDL.
* Use a deliberate operator-controlled SQL session connected to the verified target. Stop on first error and inspect transaction state. The existing files have `BEGIN`/`COMMIT`; do not wrap them in an assumed outer migration transaction. Keep an immutable operational record of file checksums, reviewed SQL, database/project/branch/deployment identity, operator, timestamps and outcomes. Establish a reviewed forward-only tracked migration process for future changes; the current SQL files are not a Drizzle migration chain, so do not simply run `drizzle-kit migrate` or insert fabricated journal entries. Baseline and drift reconciliation must be designed after inspection.
* Re-run the catalog audit and manual comparisons, verify relevant query paths and constraints/indexes, check counts and content/gallery integrity against pre-change evidence, and test admin login/history, products, UZ/RU/EN content, upload, settings, contacts, homepage and public routes using appropriate non-destructive checks. A login creates a real session record; use an approved test account. Confirm the live deployment uses the audited target. Record exact results and unresolved differences. Rollback should restore service without deleting business data; use tested recovery rather than ad hoc destructive DDL.
