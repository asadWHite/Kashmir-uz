# Kashmir Decor — multilingual content system & performance work

Date: 2026-11-13 · Branch: `arena/b49143cd-kashmir-uz` · Base: `0e841d3` (`main`)
Companion document: `docs/audit/BASELINE-2026-11-13.md` (before-state root-cause audit)

## 0. Scope and method (read this first)

**What was verified and how.** Every number in this report was produced in this sandbox
against a local PostgreSQL-compatible server (PGlite 0.5.16 / PostgreSQL 18.6 wire
protocol, `127.0.0.1:5432`) running the **real** Drizzle schema, migrations, seed data and
queries. The application was built with `next build` and served with `next start`
(Next.js 16.2.6, Turbopack). The "before" column was produced by checking out the base
commit `0e841d3` into a separate worktree, building it with the same toolchain and
benchmarking it from a second port, with both servers warm at the same time.

**What could *not* be verified here — stated plainly.** This sandbox has:
- no access to the production database (`kashmirdecor.uz` / Neon / Vercel Postgres),
- no access to Vercel runtime or Web Vitals telemetry,
- no ability to download a browser (`playwright install chromium` fails on network), so
  **no lab LCP / INP / CLS / TBT measurements exist**. Anything about real-user metric
  improvement below is a reasoned inference from byte counts, marked as such.

Consequences: the migrations were **not** run against production, no production data was
read or written, and nothing was deployed. All claims are about this repository.

**Ground rules observed.** No existing record was deleted or overwritten; no stored image
was modified (image fallbacks are read-path only); `main` was not touched or reset; there
is no destructive migration (both migrations are additive: `CREATE TABLE IF NOT EXISTS` +
`INSERT … ON CONFLICT DO NOTHING`); no per-language duplicate product rows were introduced.

## A. Root causes (what was actually wrong)

1. **Localization never consulted the database.** The UI had one hardcoded dictionary keyed
   by product slug (`CURTAINS`/`INTERIORS`/`STATS` in `src/lib/i18n.ts`, ~850 lines) and
   `src/lib/data.ts` returned raw rows. Any content an administrator created through
   `/admin` had **no** translation at all and rendered in whatever language the column was
   written in — in practice English, on every language version of the page.
2. **Content languages were conflated with the interface language.** The legacy columns
   (`curtains.name`, `interiors.title`, `categories.name`, `gallery.title`,
   `statistics.label`, `site_settings.hero_*`) are English, but the code treated them as
   the default-locale copy. A Russian visitor therefore saw English product names
   (`"Мягкий белый"` next to `"Soft white"`), and there was no way to fix it from the admin
   panel — this was the single visible multilingual defect.
3. **No cache, and everything `force-dynamic`.** Every request re-queried every table.
4. **Base64 images inline in the payload.** `image_url` could hold multi-megabyte data
   URLs, selected with the row and inlined into the HTML/RSC flight data.
5. **The admin panel could not edit translations at all** — the three language versions of
   a record were not addressable.
6. **Admin navigation lost the session.** `AdminNav`'s "view website" link was
   `<Link href="/">` inside the admin area.
7. **Lint was failing on `main`** (10 errors / 17 warnings), so "lint is clean" was not a
   true statement about the starting point.

## B. Data model (additive, reversible)

Two new tables, no change to any existing table:

```
content_translations(id, entity, entity_id, locale, title, subtitle, description,
                     seo_title, seo_description, extra jsonb, review_status,
                     created_at, updated_at)
  UNIQUE (entity, entity_id, locale)      -- one row per language per record
content_revisions(id, entity, entity_id, action, created_at)   -- cache stamp
```

- `entity ∈ {curtain, interior, category, faq, statistic, gallery, settings}`;
  `locale ∈ {uz, ru, en}` and is validated on **write**, not assumed.
- `extra` is a typed JSON bag for entity-specific strings (material, colour, style, room,
  hero eyebrow/statement, about copy) so a new localized field does not require a new column.
- `review_status ∈ {complete, needs_review, machine}` — machine-assisted text is marked so it
  can be reviewed instead of silently passing as human-written.
- **Legacy columns are retained.** They are still the value for `en` where they were authored
  in English, they keep old code paths and exports working, and they are the rollback path.
  Nothing was dropped. `LEGACY_CONTENT_LOCALE = "en"` in `src/lib/content.ts` is the single
  place that states this; it was the source of defect #2 when it was conflated with the UI
  default locale (`ru`).
- Migrations: `migrations/0002_content_translations.sql` (schema) and
  `migrations/0003_content_translations_seed.sql` (backfill of existing content into all
  three locales). Both are idempotent and were applied and verified with
  `npx tsx scripts/db-gate.ts` (13 / 5 / 10 columns, per-entity row counts checked).
  Backfilled total: **57 translation rows** (category 5, curtain 4, faq 3, interior 3,
  settings 1, statistic 3 — × 3 languages).

## C. Resolution rules on the public site

`pickText(locale, field, map, { required })` is the only way copy becomes visible:

| Situation | Result |
|---|---|
| Translation exists for the requested locale | that text |
| No translation, field is required (names, titles, FAQ questions) | localized notice, e.g. `Ushbu kontent hozircha o‘zbek tilida mavjud emas.` |
| No translation, optional field (descriptions, captions) | `null` → component renders its own layout without text |
| Requested locale is `en` and the legacy column was authored in English | legacy column (via `LEGACY_CONTENT_LOCALE`) |
| Locale is `ru`/`uz` and only legacy English exists | **notice, never English** |

The legacy value is never used as a cross-language fallback. That one decision is what
removes the English leak; the cost is that untranslated copy shows an honest notice instead
of pretending, and the admin completeness report (`/admin/translations`) shows exactly which
records need work.

Interface strings (navigation, buttons, labels) remain code-owned and translated in
`src/lib/i18n.ts`; *content* is database-owned. The two no longer mix.

## D. Admin: independent language editing

Every localized entity has the same contract:

- `PATCH /api/admin/<entity>/<id>` — translations only. Body: `{ translations: { ru: … } }`.
  Writes exactly the locales present in the body, one row each, via a single
  `INSERT … ON CONFLICT (entity, entity_id, locale) DO UPDATE`. Uzbek and English are not in
  the statement at all, so editing Russian **cannot** affect them.
- `PUT /api/admin/<entity>/<id>` — shared, non-translatable fields only (ordering, active
  flag, image, category). Omitting a field leaves it untouched.
- `DELETE` — removes the record **and** its translation rows (see F1).
- All of them call `invalidatePublicContent()`.

Server-side validation lives in `src/lib/admin-content.ts`, not in the UI, so a hand-made
request cannot bypass it:

```
unsupported locale        -> 422 «Неподдерживаемый язык «de». Допустимые языки: ru, en, uz.»
non-object locale value   -> 422
unknown reviewStatus      -> 422
empty locale payload      -> skipped, existing rows untouched
duplicate slug            -> 409
```

The UI is `TranslationEditor` (tabs UZ / РУССКИЙ / ENGLISH with per-language
`не заполнено` / `проверить` / `готово` badges). It is used by curtains, interiors,
categories, FAQ, gallery, statistics and the homepage-copy/settings screen. One language
keeps its own draft object, so switching tabs never remaps or resets a field, and an
all-empty draft is never submitted (which would otherwise be a silent erase).

`/admin/translations` is a new server-rendered completeness report per entity: per row it
lists which languages are `нет:` (missing) or `проверить:` (needs review), with totals per
language at the top.

## E. Caching and immediate propagation

Public pages are still dynamic per locale (the language is a cookie, not a URL segment), but
the data underneath is cached:

- `unstable_cache` — **not** `"use cache"`. The directive requires the experimental
  `cacheComponents` flag and the build rejects it (`please enable the feature flag
  cacheComponents`); this project runs stable Next 16, so the stable API is the correct
  choice.
- Cache key is `key:locale:revision`. The locale is part of the key, so one language can
  never be served from another language's entry. The revision is the newest
  `content_revisions.id`, read through a 1-second cache — at most one tiny indexed query per
  second per instance, shared by all pages.
- Any admin write inserts a revision and calls `revalidateTag(tag, "max")`. The revision is
  shared state, so on a multi-instance deploy (Vercel) every instance picks up the new
  content on its next revision read (≤1 s), not after a TTL. A per-process invalidation
  alone would only reach the instance that served the write.

## F. Defects found *while verifying* (found and fixed, not deferred)

These were discovered because the verification was end-to-end rather than by inspection:

1. **Deleting a record orphaned its translations.** `content_translations` is polymorphic
   (`entity` + `entity_id`) and cannot have a foreign key, so nothing in the database cleans
   it up. Deleted rows would stay forever and be re-attached by id to any future record that
   reused the number. Fixed with `deleteTranslations()` called before every delete (curtain,
   interior, category, faq, gallery, statistic). Purging counts during cleanup confirmed the
   leak was real (6 orphan rows removed from the local DB).
2. **A Cyrillic- or Uzbek-only title produced an empty or wrong slug.** The inline `slugify`
   kept only `[a-z0-9]`, so «Современные бархатные шторы» became `""` — an unreachable page,
   and the second such record crashed on the unique index. Replaced by
   `src/lib/slug.ts`: Cyrillic + Uzbek transliteration
   (`"Современные бархатные шторы"` → `sovremennye-barkhatnye-shtory`), diacritic folding,
   and a stable prefix fallback if a title has no representable characters.
3. **Duplicate slug returned 500.** Now `409` with an actionable message, detected through
   the driver's wrapped `cause` chain (`isUniqueViolation`).
4. **"Clear a field" silently did nothing.** The `hasText` filter on the payload was applied
   to the stringified row object, so it was always truthy and an all-empty payload survived
   the filter; the intent (skip empty locales, never erase) was only enforced in the UI.
   Fixed in the server: the filter now inspects the actual fields.
5. **Hero lost its `fetchPriority="high"`.** Switching the hero to `next/image` dropped the
   explicit hint (the preload was emitted with `imageSrcSet` but no priority). `MediaImage`
   now sets `fetchPriority="high"` on priority images; the rendered preload carries it again.

## G. Measured results

### G1. Server response time (20 iterations after 2 warm-ups, warm servers, same host)

Both servers were running simultaneously, both against the same local DB.

| Route | before avg / p50 / p95 | after avg / p50 / p95 |
|---|---|---|
| `/` | 24.6 / 20.2 / 37.5 ms | 19.7 / 18.0 / 34.8 ms |
| `/collections` | 17.2 / 16.0 / 37.9 ms | 15.7 / 15.3 / 23.3 ms |
| `/interiors` | 14.6 / 15.2 / 19.2 ms | 12.8 / 12.1 / 22.6 ms |
| `/gallery` | 12.9 / 12.2 / 22.2 ms | 16.7 / 13.8 / 54.8 ms |
| `/curtains/graphite-velvet` | 14.8 / 14.1 / 25.6 ms | 20.7 / 19.2 / 28.0 ms |

**Honest reading:** `/`, `/collections` and `/interiors` improved; `/gallery` and the product
page did not. The product page is slower because it now resolves translations for the record
*and* its related items, and because the local PGlite wire server serialises all queries
through one process — a real Postgres will not behave this way, but that is an expectation,
not a measurement here, and it is not presented as a win. The server-time change is not
where this work pays off; see G2–G4.

Note on the HTML column: HTML/raw bytes **grew** on every route (e.g. product page 24.6 →
36.0 KB raw). That is expected and is not a regression in transfer size: the mark-up now
carries `srcset` candidates, `sizes`, and full Russian/Uzbek copy that previously did not
exist at all. Gzipped size grew by only 0.5–1.3 KB (see G3).

### G2. Image delivery (the dominant win)

`next/image` + AVIF/WebP + explicit `sizes`, with curated assets in `/assets`:

| Asset | before (single file, every device) | after (AVIF at that width) |
|---|---|---|
| hero, 360 px viewport | 205 KB | **5 KB** |
| hero, 640 px | 205 KB | 12 KB |
| hero, 1024 px | 205 KB | 28 KB |
| hero, 1920 px | 205 KB | 59 KB |
| card (`curtain-01`), 640 px | 256 KB | **20 KB** |

A phone previously downloaded 205 KB of hero; it now downloads 5 KB — a **97.5 % reduction**
for the largest element on the page. This is the change most likely to move real LCP, though
again: **no browser LCP number was measured here**.

All nine `<img>` on the homepage now go through `/_next/image` with `srcset` (verified: 9/9,
1 eager with `fetchPriority="high"`, 8 lazy). Previously: 0/9 optimised, 0 `srcset`.
Stored data URLs larger than 200 KB are replaced on read with the curated fallback so they
are never inlined into a document; the stored value is untouched (`src/lib/media.ts`).

### G3. Payload (gzip, what actually crosses the wire)

| Route | before | after (ru) | after (uz) |
|---|---|---|---|
| `/` | 12.7 KB | 13.3 KB | 12.5 KB |
| `/collections` | 6.7 KB | 7.5 KB | 7.0 KB |
| `/interiors` | 6.1 KB | 6.7 KB | 6.3 KB |
| `/gallery` | 6.0 KB | 6.8 KB | 6.5 KB |
| `/curtains/graphite-velvet` | 5.8 KB | 7.1 KB | 6.8 KB |

Two of the five routes are byte-for-byte **smaller** in Uzbek than before the change, while
rendering three real languages instead of one English. The product page is ~1.3 KB heavier
because it now carries actual localized copy and `srcset` candidates. This is the honest
trade: a small document cost for content that is no longer language-incoherent, against an
image cost that fell by 97 % on the first screen.

### G4. Client JavaScript

| Measure | before | after |
|---|---|---|
| `/_next/static/chunks` total (all files on disk) | 996 KB | 1044 KB |
| JS on a public page (11 files, uncompressed) | 693 KB | 706 KB |
| same, gzip | 206 KB | 211 KB |

Client JS **grew by ~5 KB gzip**, it did not shrink. The ~850-line dictionary is no longer
the content source, but it was never removed from the bundle — it is still imported for
interface strings. Reporting a bundle win here would be false. Removing it would mean
splitting interface copy from content copy and editing every component that calls `t()`;
that is a real, separate piece of work, listed in §H rather than claimed as done.

What did improve in the client layer: the lint-driven rewrites all replaced
`useState`+`useEffect` pairs with `useSyncExternalStore` or imperative DOM
(`Cursor`, `ThemeToggle`, `LikeButton`, `useLocalState`, `Statistics`), which removes
mount-time cascading renders and the associated flicker — a correctness/INP-proxy
improvement, not a measured one.

### G5. Quality gates

| Gate | before (`main`) | after |
|---|---|---|
| `npx tsc --noEmit` | pass | **0 errors** |
| `npx eslint .` | **10 errors / 17 warnings** | **0 errors / 0 warnings** |
| `npm run build` | pass | **pass** (all routes) |

Every lint error was fixed by changing the code; no `eslint-disable` was added for them and
none of the rules were downgraded.

### G6. End-to-end behaviour verified against the running server

- Strict language isolation: `/`, `/collections`, `/interiors`, `/interiors/<slug>`,
  `/gallery`, `/curtains/<slug>` each checked for UZ / RU / EN; **no cross-language text
  present** in any of them.
- Metadata follows the same locale: product `<title>`/`<meta description>`/`<h1>` differ
  correctly per cookie (e.g. `Grafit baxmal` / `Графитовый бархат` / `Graphite Velvet`).
- Admin login → create a record with three languages → all three public pages correct →
  `PATCH` **only** `ru` → Russian updates, Uzbek and English unchanged on the public site.
- Unsupported locale rejected `422`; duplicate slug `409`; Cyrillic-only title gets a real
  slug and a `200` page.
- An English-only record: `en` renders its text, `uz`/`ru` render the localized notice and
  **zero English** from that record.
- `/admin*` is `noindex, nofollow` in both the `X-Robots-Tag` header and the HTML meta tag
  (checked on `/admin`, `/admin/translations`, `/admin/curtains`, `/admin/gallery`,
  `/admin/statistics`).
- Public responses carry `Content-Language: ru, uz, en`; `/sitemap.xml` and public routes
  carry `Vary: Cookie`.
- `/_next/image` returns `image/avif` with `Cache-Control: public, max-age=2592000`.

## H. Remaining risks and unfinished work

**Deliberate design decisions (not defects):**
- **One canonical URL per page; the language is a cookie.** There is no `?lang=` and no
  `/uz/` prefix. This avoids duplicate-content and wrong-hreflang classes of bug, and it
  means a shared link opens in the recipient's own language. It also means the three
  language versions are **not separately indexable** — a real SEO trade-off, documented in
  `src/lib/site.ts` / `src/lib/seo.ts` usage. `og:locale` and `alternateLocale` are emitted,
  hreflang is deliberately not.
- **Untranslated content shows a notice, not English.** That is the point, but it does mean
  the quality of the UZ/RU site now depends on completing the backfill. The backfill used
  the existing seed copy; anything an administrator wrote in English only will show a notice
  in RU/UZ until translated. `/admin/translations` exists precisely to make that visible and
  finite.
- **Interface copy still lives in code** (see G4). Content and interface copy are now
  separate concepts but not yet separate bundles.

**Still open, in priority order:**
1. **Production-safe migration run.** `scripts/db-gate.ts` is ready and idempotent, but it was
   only ever run against the local database. It must be run against the production
   `DATABASE_URL` (backup first) before deploy. Nothing in this branch deploys itself.
2. **Real measurement.** LCP/INP/CLS need a browser and production traffic. The 97 % hero-byte
   reduction makes an LCP improvement very likely, but it is an inference, not a measurement.
3. **Bundle split** for the ~850-line interface dictionary (G4). Mechanical but wide: touches
   every `t()` call site.
4. **Review status workflow.** `needs_review` / `machine` are stored and displayed but there is
   no "mark as reviewed in bulk" action yet.
5. **Product-page server time** (G1) should be re-measured against real Postgres; the local
   single-process wire server is the wrong instrument for that comparison.
6. **Exhaustive visual regression across browsers** is unverified — no browser was available.
   Layout was preserved structurally (`object-cover`, same aspect containers, same `sizes`
   intent), not pixel-compared.
7. **Delete is still a hard delete** for content records. It is now correct (translations go
   with the record) but not recoverable. A soft-delete/undo path would be the safer default
   and is the next data-integrity improvement.
